# Game library identity audit

Phase 0 of the game identity overhaul
([#91](https://github.com/obsoletelabs/unnamed_tracking_app_2/issues/91)), delivered for
[#92](https://github.com/obsoletelabs/unnamed_tracking_app_2/issues/92). It records how the
game library, duplicate review and the Playnite integration work **today**, so the schema
and contract work in #93–#103 starts from the code rather than from the target design.

- **Baseline:** `main` at `f93fa78` (#156), audited 2026-10-16. Paths are relative to the
  repository root; backend paths start `src/backend/src/`, written below as `backend/…`.
- **Scope:** no application behaviour or schema changes. The audit adds this page and one
  test-only file, `src/backend/tests/test_playnite_contract.py`, which pins the Playnite
  HTTP contract described in [section 6](#6-playnite-integration).
- **Not inspected:** the Playnite extension's own source (`UnnamedTrackingPlaynite`, now
  `obsoletelabs/unnamed_tracking_playnite`) was not available to this audit. Section 6
  therefore documents the host side of the contract plus what the host repository already
  records about the extension ([Playnite](../integrations/playnite.md) and the
  [2026-10-03 acceptance](post-merge-acceptance-2026-10-03.md)). Items marked
  *unverified* must be confirmed against the extension source in #100 before its contract
  changes. `obsoletelabs/unnamed_tracking_app_plugins` contains no Playnite code; its Epic
  Games plugin is the only official `games.import` consumer and was read for section 5.1.

## 1. Rollout prohibitions

Every child issue of #91 must follow these rules. They restate the epic's invariants as
checks a reviewer can apply to a diff.

| # | Prohibited | Practical test |
| --- | --- | --- |
| P1 | **Destructive deduplication.** A merge is a relationship or decision row; it never deletes, overwrites or folds together `games` rows, achievements, notes, files or folders. | A merge followed by an unmerge restores every original row byte-for-byte. |
| P2 | **Source-row deletion.** Source identities (`external_id`, `playnite_guid`, plugin `games.id`, `provider_ids`, provider achievements) survive merge, split, rename and disconnect. Disconnect clears credentials only, as it does today. | No migration or service issues `DELETE` against a source identity; archived/disconnected observations stay queryable. |
| P3 | **Inferring removal from incomplete data.** Partial, failed, cancelled or paginated-incomplete inventories never mark items deleted, unowned or reset. | Availability changes only after a complete inventory or an explicit `available: false`. |
| P4 | **Breaking Playnite in any phase.** The endpoints in [section 6.2](#62-endpoint-contract) keep their request shapes, response shapes and status codes until a versioned replacement ships and the extension has moved to it. | `tests/test_playnite_contract.py` and the Playnite tests in `tests/test_games.py` stay green without edits, except a deliberate, documented contract version change agreed in #100. |
| P5 | **Weakening CI.** No deleted, skipped or loosened tests, no disabled jobs, no lowered thresholds. | The baseline in [section 10](#10-test-commands-and-baseline-results) only grows. |
| P6 | **Rewriting existing game IDs.** Every current `games.id` stays addressable: routes, bookmarks, child foreign keys, plugin replay identities, legacy exports and external clients depend on it. | A new umbrella identity is additive; existing IDs resolve after every migration. |
| P7 | **Automatic merges from weak evidence.** No automatic association from titles alone or from an incomplete inventory; explicit user decisions always win. | Auto-association needs the explicit, tested rule set from #99. |
| P8 | **Destructive resets.** No drop-and-reimport, no dropped columns or tables until every consumer has moved and a separate cleanup is reviewed. | Autogenerated migrations are reviewed; retained legacy tables stay (see [H22](#h22)). |
| P9 | **Using the JSON export or scheduled backup as a rollback.** It loses identities ([H15](#h15)). | Upgrade notes for #102 require a database dump (`pg_dump`) and data-folder copy. |

## 2. Architecture at a glance

One `games` row (`backend/database/models/game.py::Game`) is currently the logical game,
the edition/platform copy, the imported source record, the personal tracking record and the
storage folder, all at once. Everything else hangs off `games.id`.

```text
users ─┬─ games ─────────────┬─ game_links (labels/URLs)
       │   ├ parent_game_id ─┘   achievements ── media_items / game_note_details (linked achievement)
       │   │  (owned_copy, dlc,  achievement_overrides (manual + self-reported)
       │   │   mod, expansion…)  game_field_changes (partial history)
       │   │                     game_note_details ── game_note_versions (+ markdown files on disk)
       │   │                     game_profiles ── game_checklist_items, game_profile_stat_snapshots
       │   │                     game_archives ── game_archive_versions (saves; files on disk)
       │   │                     game_file_items, media_items (files on disk)
       │   │                     cards, bounties (retired, retained, exported read-only)
       └─ game_duplicate_dismissals (user's "keep both" decisions, ordered game pair)
```

Request flow follows the repository convention: `backend/api/routes/*` → `backend/features/*`
→ models. Game writes enter through five creation paths
([section 5.1](#51-creation-and-adoption-paths)); all of them end in
`backend/api/routes/games.py::create_game`,
`backend/features/imports/library_games.py::get_or_create_game` or
`backend/api/routes/export_import.py::import_library`.

### 3.3 References without foreign keys

These hold a `games.id` that no constraint protects, so a migration cannot discover them
from the catalogue: `calendar_events.media_id`; plugin storage and external clients (the
Epic plugin keeps external IDs, not game IDs; the Playnite extension's local state is
*unverified*); browser routes and bookmarks (`/games/{id}`) and front-end caches
(`frontend/src/services/games.ts` entity cache); scheduled backups in `/data/backups`;
the on-disk trash folder named after the game ID ([H16](#h16)).

## 4. Stable identifiers and invariants

| ID | Where it is produced | Uniqueness and scope | Invariant |
| --- | --- | --- | --- |
| `games.id` (manual, host sync, JSON import) | `uuid4` default in `models/game.py` | Global PK | Immutable; children, URLs and clients depend on it |
| `games.id` (plugin `games.import`) | `plugin_api/game_import.py::game_import_identity`: `uuid5(NAMESPACE_URL, json(["plugin-game-v1", plugin_id, user_id, source_scope, external_id]))` | Global PK; deterministic | **The row ID is the replay key.** Retries, renames and label changes resolve to the same row (`tests/test_plugin_game_import.py`). Changing it breaks every installed store plugin. |
| `folder_location` | form input, `library_games.py::LibraryIndex.claim_folder`, `export_import.py::_available_folder_location` | Unique among a user's active rows (`ix_games_user_folder_location_active`) | It is the storage path `/data/users/<user_id>/games/<folder_location>/` for artwork, notes, media, saves and files (`helpers/save_game_asset.py::create_game_folder`), and Playnite's first matching key |
| `playnite_guid` | Playnite create/update payloads | Indexed, **not unique**, not scoped to a Playnite library | `create_game` reconciles by GUID, then adopts an unclaimed folder match by stamping the GUID; a folder owned by another GUID is HTTP 409 |
| `(user_id, source, external_id)` for `Steam`, `RetroAchievements`, `PlayStation` | `api/routes/library_sync.py` and `steam_import_steps.py` via `get_or_create_game` | Enforced only by `LibraryIndex`/`_find` under row locks and `features/connection_jobs.py::sync_scope` (in-process) | When the import carries an ID, the title fallback adopts only rows without an `external_id`; distinct IDs with equal titles stay distinct (`tests/test_library_sync_efficiency.py`) |
| `provider_ids` | metadata search/select, refresh, enrichment, plugin imports | JSONB map, namespace keys `^[a-z0-9._-]+$` | Merged additively, never pruned; drives duplicate `shared_identity` evidence and metadata resolution |
| Achievement identity `(game_id, provider, external_id)` | `library_sync.py::_replace_achievements` | Application-enforced upsert, no constraint | Rows missing from a **non-empty** provider list are deleted; an empty or unavailable list keeps stored rows (`tests/test_achievements.py::test_an_empty_answer_does_not_wipe_stored_achievements`) |
| Manual/self-reported achievement | `features/delegated_library.py::write_achievement_report` | Unique `(game_id, provider, external_id)`; manual rows use the supplied external ID or a generated `uuid4` | Survive provider reimports (`tests/test_delegation.py::test_achievement_report_survives_provider_reimport_and_stays_self_reported`) |
| Keep-both decision | `features/game_duplicates.py::keep_both` | Ordered pair per user | Imports never write it; replays keep it |
| Owned-copy group | `features/game_ownership.py::group_copy` | `parent_game_id` + `relationship_type='owned_copy'`, one level, main must be standalone | Never merges fields, files, achievements or provider bindings; `separate_copy` reverses it |
| Connection job ID | `features/connection_jobs.py::connection_job_id` | `uuid5(user_id, provider)` | Stable across disconnects and credential changes |
| Metadata candidate ID | `features/metadata/identity.py::candidate_id` | `uuid5` of media type, provider and external ID | Search-result identity only; not stored on games |

Further invariants the redesign must keep:

- **User isolation.** Every game query filters `user_id`; plugin identities include
  `user_id`; cross-user access returns 404 (`tests/test_playnite_contract.py::test_a_key_only_reaches_its_own_users_library`).
- **Protected metadata.** `features/metadata/locked_fields.py`: refresh and imports skip
  `locked_fields`; only a browser session can change a locked title or `title_lock`
  (`core/auth.py::AuthenticatedActor.can_manage_protected_metadata`).
- **Conservative status progression.** `features/imports/game_progression.py::apply_provider_progress`
  only advances `BACKLOG` and `WISHLIST`, and Wishlist only with ownership evidence.
- **Soft deletion.** `DELETE /api/game/delete/{id}` sets `deleted_at` and moves the folder to
  trash; `features/trash/sweep.py` purges after seven days. Plugin imports never restore Trash.

### 5.3 Duplicate review and owned copies (#56)

Issue #56 was closed on 2026-10-11 as resolved by the all-provider duplicate review and
owned-copy grouping (its closing comment cites PR46 and PR48 and a browser acceptance at
320, 390 and 1440 pixels). The current behaviour:

1. **Detection** — `GET /api/game-duplicates` (`api/routes/game_duplicates.py`,
   `features/game_duplicates.py::suggestions`) reads compact active rows once, groups them by
   `match_key(title)` (NFKC, casefold, trademark and apostrophe removal, punctuation to
   spaces) and by every `provider_ids` entry, and emits pairs with reason `same_title` or
   `shared_identity`. `compatible()` drops pairs with conflicting known platform,
   relationship type, release year, shared provider IDs, or same-source different
   `external_id`, and drops any row that already has a `parent_game_id` (grouped copies,
   DLC, mods). Responses are bounded (`limit` 1–100, default 50, `has_more`). No provider
   calls are made.
2. **Highlighting** — `frontend/src/composables/useGameLibrary.ts::loadGames` fetches the
   default 50 pairs and marks both games; `components/GameCard.vue` and the list view in
   `views/GameLibrary.vue` show **Review possible duplicate**, linking to
   `/settings?section=library&tab=duplicates`. A failed check shows nothing rather than
   claiming uniqueness.
3. **Review** — `components/settings/DuplicateGamesSection.vue` compares source, platform,
   release year, status, playtime, import ID, provider IDs and protected-field count.
   **Keep both** calls `POST /api/game-duplicates/keep-both` (idempotent, order-insensitive,
   both games must be active and owned). **Group owned copies** opens
   `components/game/GroupGameCopiesDialog.vue`, which calls `POST /api/game-ownership/group`.
4. **Grouping** — `features/game_ownership.py` serializes per user with an advisory lock,
   requires a standalone main, allows one level, rejects regrouping a copy that already has
   another parent, and never touches the copy's fields, files, achievements or identities.
   `POST /api/game-ownership/separate` needs the expected main ID so a stale request cannot
   split a newer group. `frontend/src/utils/gameOwnership.ts::gameOwnershipGroups` collapses
   copies under their main in the library; a copy whose main is trashed shows on its own.
   Search and filters match any copy (`copiesOf`).
5. **Copy panel** — `components/game/GameOwnedCopiesPanel.vue` lists each copy and **sums**
   their playtime; provider overlap is not deduplicated (documented in
   [Games](../user-guide/games.md#owned-copies)).

Covered by `tests/test_game_duplicates.py` (14), `tests/test_game_ownership.py` (11) and
`frontend/src/tests/gameOwnership.test.ts`. Gaps for #99 are listed in [H13](#h13).

### 5.4 Playtime, last played, completion and achievements

- **Playtime** is one integer per row. Steam overwrites it each sync
  (`test_owned_steam_uses_reported_playtime_not_a_locally_saved_value`), plugins keep the
  maximum, Playnite and the UI set it, RetroAchievements and PSN do not report it.
- **Last played** is written only by Steam sync. It is not accepted by create, update or
  JSON import, so Playnite cannot send it today.
- **Completion** is `status` plus `completion_date`. Provider evidence only advances Backlog
  and Wishlist. Existing Played/Beaten/Mastered values cannot be attributed to a person or a
  sync (stated in `game_progression.py`).
- **Achievements** are provider rows only in `GET /api/game/{id}/achievements`,
  `GET /api/game/achievements-summary` and statistics. Manual achievements and
  self-reported unlocks exist only in `achievement_overrides` behind the delegation API
  (`/api/delegation/v1/games/{id}/achievement-reports`); the main UI does not read them.
- **Aggregation** — `GET /api/stats/overview` (`api/routes/stats.py::_overview_queries`) sums
  `playtime_seconds` over every row of the user, including grouped copies and trashed games
  ([H14](#h14)). `GET /api/media-stats` game sections (`api/routes/media_stats.py`,
  `features/game_stats.py`) exclude trash but still sum copies.

### 5.5 Source disconnect

Steam (`features/imports/steam_connection.py::disconnect`) and PlayStation
(`DELETE /api/auth/me/psn`) clear credential fields on `users` and leave games,
achievements and identities untouched. Connection credentials live on the `users` row, so
each user has one account per host provider and imported rows carry no account scope.
Plugin connections scope identity by `source_scope`; disconnecting a plugin account does not
touch games. Playnite has no server-side connection record: revoking its API key stops
access and changes nothing in the library.

### 5.6 Titles, placeholders and artwork

- `Steam app <appid>` is the wishlist placeholder (`steam_import_steps.py::_PLACEHOLDER`).
  It is repaired only by Steam enrichment of the rows that import just created
  (`library_sync.py::_enrich_new_game`, case-sensitive `startswith("Steam app ")`, skipped
  when the title is locked) or by a later owned-library sync reporting the real name.
  `POST /api/game/{id}/metadata/refresh` cannot repair it: it only applies a result whose
  normalized title equals the current title.
- Every host and plugin import applies the provider's current title through
  `apply_metadata_updates`, so a provider rename renames the game unless the title is locked.
  No raw source title is stored separately; `game_field_changes` does not track `title`.
- Artwork is one file per kind (`key_art`, `banner`, `logo`, `icon`) in the game folder with
  no provenance; any upload replaces it. Per the Playnite page, the extension uploads cover
  and banner when it creates a game.

### 5.7 Search, collections, series and relationships

- **Library search** is client-side: `useGameLibrary.ts::fuzzyTitleMatch` (substring, then a
  per-word edit-distance for queries of four or more characters) over every copy in a
  group. `GET /api/game/list?search=` is a plain `ILIKE` on `title`.
- **Metadata search ranking** is `features/metadata/identity.py::rank_key` (exact or
  alternate title, similarity, token overlap, provider priority, stable tie-breaks).
  `identity.py::normalized_title` (alphanumerics only) differs from duplicate review's
  `match_key` (keeps word boundaries).
- **Collections** are names in `games.collections`; imports add the source and the series
  name to new rows only. **Series** is a free-text column. **Variants** come from
  `GET /api/game/{id}/variants` (children by `parent_game_id`).

### 5.8 Notes, history and audit data

`games.notes` is a text column that Playnite overwrites. Rich notes are markdown files in
the game folder with `game_note_details`/`game_note_versions` metadata
(`features/game_notes.py`). `game_field_changes` records only
`api/routes/utils/games.py::FIELD_CHANGE_TRACKED_FIELDS` and only from `update_game` and
metadata refresh; sync writes, titles, playtime and identity decisions have no history.
Duplicate decisions keep only `created_at`, with no actor or reason.

### 5.9 Deletion and cascades

User and game deletion depend on the database rules in [section 3.1](#31-tables).
`User` declares no ORM relationships, so `DELETE /api/auth/users/{id}` relies entirely on
`ON DELETE CASCADE`, which `game_links` blocks ([H3](#h3)). Game deletion is soft; the sweep
deletes the ORM object, so `Game.links`' ORM cascade removes links first. Purging a game
removes its duplicate decisions, achievements, overrides, notes metadata, history and files
metadata through cascades.

## 6. Playnite integration

### 6.1 Connection and authentication model

- The extension authenticates every request with `Authorization: Bearer utk_…`, a personal
  API key created from a browser session (`POST /api/auth/api-keys` rejects API-key
  callers). `core/auth.py::get_current_user` accepts it on every normal game route and
  records the actor as `credential_kind="api_key"`.
- Key `scopes` are stored but not enforced: a key has full access to its user's library.
- There is no Playnite connection, library, installation or device record on the server.
  `playnite_guid` is not scoped by library, and several Playnite libraries may use one
  account. The Plugin API's scoped device identities (`docs/plugin-validation.md`,
  `PlayniteValidationPlugin`) are a validation example only; the extension does not use them.
- Bodies over 1 MB are pre-authenticated by `api/request_bodies.py` (#156) using the same
  `get_current_user`, so API-key artwork and save uploads still pass
  (`test_artwork_over_one_megabyte_uploads_with_the_api_key`).

### 6.4 Current contract hazards

- **Second rename fails** ([H7](#h7)). An API-key title change locks the title, and the next
  API-key title change returns 403 for the whole PATCH, including playtime and status
  (`tests/test_title_protection_api.py::test_api_unprotected_edit_remains_usable_and_automatically_locks`).
  How the extension reports or retries this is *unverified*.
- **Playnite writes look like manual edits** (at audit time; fixed in #100, see [Playnite observations](playnite-observations.md)).** Changed metadata fields joined `locked_fields`,
  so later metadata refreshes skip them, and #98 cannot tell user locks from Playnite locks.
- **Last writer wins.** Each sync overwrites `status`, `playtime_seconds`, `favorite`,
  `notes` and ratings with Playnite's values; there is no provenance or conflict.
- **No last played, achievements or platform/edition** reached the host from Playnite at audit time (platform, last played and installed state now travel through the [observation API](playnite-observations.md); Playnite has no achievements).
- **Trash.** `_find_playnite_game` ignores trashed rows, so a sync after deleting a
  Playnite game creates a new row; restoring the old one then fails with a folder 409.

### 6.5 Required contract changes and compatibility strategy

| Change (owner) | Compatibility rule |
| --- | --- |
| Map Playnite writes to source observations keyed `(user_id, "playnite", <library scope>, playnite_guid)` (#94, #100) | Keep `POST /api/game/create` and `PATCH /api/game/update/{id}` as a compatibility adapter that records an observation **and** applies today's effective write. Legacy rows get a `legacy` library scope; the GUID alone remains a valid key. |
| Separate Playnite provenance from user locks (#98, #100) | Writes from an API-key actor on the legacy endpoints are recorded as Playnite observations; existing `locked_fields` stay locked (conservative). Remove the auto-lock for API-key writes only once provenance exists, with the contract test updated deliberately. |
| Let renames through without a 403 (#98, #100) | A Playnite title becomes the observed source name; the effective title follows the name-quality and lock rules instead of rejecting the request. Old extensions keep sending `title` and must not see new 4xx responses. |
| Per-metric playtime, completion and achievements (#96, #97, #100) | Playnite values become one counter's observations; manual adjustments and manual completion survive. The legacy PATCH keeps returning the effective `GameRead`. |
| A versioned ingestion endpoint (#94, #100) | Additive and discoverable (for example a capabilities document or versioned path). The extension uses it only when advertised; servers keep the legacy endpoints for at least one released extension version after the new one ships. |
| Library/installation scope for GUIDs (#100) | Optional field; absent means the legacy scope. Never re-key existing rows by guessing a library. |
| Trash handling for Playnite creates (#94, #100) | Decide explicitly (report conflict like plugin imports, or restore); never silently create a second identity for the same GUID. |

Release order: the host ships the adapter first and stays compatible with the current
extension (0.1.2 per the acceptance record); the extension then adopts the new endpoint;
the legacy path is retired only by a separate, reviewed change.

## 7. Mapping to the proposed model (#93)

| Concept | Current representation | Gap | Migration source (#102) |
| --- | --- | --- | --- |
| Canonical game / umbrella | A standalone `games` row, or the main of an owned-copy group | No entity above a row | One umbrella per standalone row; one per owned-copy group with the main as its first identity |
| Version / edition / platform identity | The `games` row (`platform`, `region`, `language`); owned copies | Platform and edition are columns, not identities | **Keep each `games.id` as a tracked identity** (P6); attach it to its umbrella |
| Source observation | Implicit in the row: `(source, external_id)`, `playnite_guid`, plugin `uuid5` ID, `provider_ids` | No table, no raw payload, no per-observation timestamps | One observation per present identity; plugin observations keyed by the existing `uuid5`; Playnite by GUID |
| Source identity | Same | Steam/PSN/RA have no account scope | Account scope `legacy` until a sync supplies one |
| Identity decision | `game_duplicate_dismissals` (separate); `owned_copy` (same) | No actor, reason, evidence or undo state | Dismissal → confirmed separate; `owned_copy` → confirmed same; both marked `migrated` |
| Relationship | `parent_game_id` + `relationship_type` | One parent, mixes copies with DLC/mods | Non-copy types become typed relationships; the column stays until consumers move |
| Counter group | None; each row is one counter | Copies are summed regardless of overlap | One counter per existing row; no automatic grouping (P7) |
| Metric provenance | None per metric; `stale_since`; `achievements.provider` | Cannot explain effective values | Seed provenance `legacy`; first new sync adds observations |
| Field provenance | `locked_fields`, partial `game_field_changes` | Locks conflate user and Playnite writes | Existing locks become user-or-unknown locks |
| Manual tracking | `status`, `completion_date`, `achievement_overrides` | Status is ambiguous; manual achievements invisible in UI | Existing status treated as user-owned; overrides retained as manual facts |

## 8. Fields with ambiguous semantics

| Field | Ambiguity |
| --- | --- |
| `source` | Free text: an import label (`Steam`), a store chosen by hand (`GOG`, `physical`) or a plugin `source_label`; host stale flags key on it |
| `external_id` | Meaning depends on `source`; unscoped by account; not exported; not writable by API |
| `provider_ids` | Mixes metadata identities and import identities; never pruned, so a wrong match persists |
| `playnite_guid` | No library scope; also adopted onto manual rows by folder match |
| `folder_location` | Storage path and Playnite match key at once |
| `title` | Display name, user override and latest source name in one column |
| `status`, `completion_date` | Manual or automatic origin is unknown for existing rows |
| `playtime_seconds` | Replaced (Steam, Playnite, UI) or maximised (plugins) depending on the writer |
| `last_played_at` | Steam-only; `GameRead` calls it never user-editable |
| `stale_since` | One availability flag for whichever source owns the row |
| `locked_fields` | User intent or an API-key client's write |
| `relationship_type` | `owned_copy` (same game) versus DLC/mod (different game) in one pointer |
| `notes` | Column overwritten by Playnite, unrelated to markdown notes |
| `collections`, `series` | Names, not entities; auto-added on import |
